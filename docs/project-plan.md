更新日期：2026-10-23。

## 协作方式

主代理负责整体推进、任务分配、方案整合、实现与验收，可根据需要使用 sub agent。用户确认影响体验或实现方向的关键决策，并可随时补充想法；主代理评估影响、调整计划并同步相关代理。常规、可逆的实现细节由主代理处理。

用户补充想法时，主代理及时与已确认方向及当前假设对照：兼容则更新计划并通知相关代理；冲突则尽快说明冲突点、影响和建议，暂停依赖该选择的工作，待讨论达成一致后继续。独立工作继续推进，不把沉默当作关键提案的批准。

工程协作使用隔离 worktree，不走 PR；由任务发起者本地 review，按 [AGENTS.md](../AGENTS.md) 的串行集成流程合入本地 `main`，关键版本或里程碑再集中 push。本地集成前检查本地主干变化，发布前再 fetch 并处理远端变化。先确认远端状态和初始提交，再启用正常 worktree 分工。首轮资料在初始 checkout 中按文件所有权隔离。

关键决定确认后，先更新本文件，再调整玩法、案件、技术方案与实现。原始 `tmp/context.md` 保留为背景草稿；其中“两名嫌疑人”的建议已由最新用户决定替换。

## 里程碑

### M0 — 明确第一局的体验与验证范围

- 完成玩法提案和案件候选，标注需要用户确认的选择。
- 建立灵矽文档事实与技术未知项清单。
- 设计内容包、通用引擎、角色可见信息与供应商适配的边界；增加同玩法游戏无需修改通用代码。
- 架构初稿给出模块职责、接口、依赖、可并行工作包和自动化测试策略，用户确认后才开始应用实现。
- 用户已独立授权最小 Cloudflare/Linx 技术探针；该验证可先进行，不视作正式六模块设计已批准。
- 确认第一案及核心交互方式；形成可人工模拟的案件骨架。

完成条件：用户可评审具体方案并确认初始模块架构；案件和技术方向的重要未知项有明确验证动作。本关口已获用户确认（D30）。

### M1 — 验证案件推理与真实对话链路

内容线和工程线并行：

- 人工模拟三名嫌疑人的审讯，检查对话中的信息差、排除过程、关键谎言与最终解释是否成立。
- 用真实灵矽配置验证一名角色的语音问答、文字事件和一次打断。
- 验证公共背景、当前角色纯文本设定与本人历史经端侧工具进入对话，不混入其他角色设定或结局。
- 验证 A → B → C → A 的历史边界，以及结束后开始新局时的隔离。

完成条件：存在完整解题路径；语音、角色上下文和会话边界有实测记录。文档描述和本地模拟不能替代真实接入验证。

### M2 — 实现第一局完整游戏

- 实现接案、语音审讯、按钮指认、反馈、重开的闭环。
- 使用公共背景与角色设定纯文本；程序维护会话并比较最终指认与固定答案。
- 使用独立的最小测试内容包验证新增游戏只改内容，测试不同角色数、局隔离及秘密信息过滤；首版只公开一个成品游戏。
- 处理麦克风权限、等待、播放、打断和基本错误恢复。
- 规则、投影、协议适配、状态隔离和核心流程等适合自动化验证的模块随实现交付测试；供应商替身用于模块独立测试，真实服务另做集成与场景评估。

完成条件：在目标桌面浏览器中能从开局走到结案并重新开始，具备必要的记录以复现问题。

### M3 — 盲测、修正与演示交付

- 请未读过剧本的玩家试玩，观察获取线索、卡关、推理和结案过程。
- 检查跨角色泄漏、关键事实编造、将玩家虚构信息当成事实、提前揭底、误判和跨局残留。
- 检查实际延迟、单局时长、调用成本与演示额度。
- 部署演示入口，准备介绍、演示流程和故障备用材料。

完成条件：陌生玩家能独立完成一局；关键规则成立；可重复运行演示。

## 工作顺序与变更原则

- 优先证明案件能被推理、角色可控、语音链路可用；案件与接入预研可以并行。
- 全案真相用于设计与判定；角色运行时只获得其允许知道的信息。
- 三名嫌疑人和纯语音沟通是已确认范围；不再规划证据元素，时长随试玩调整。
- 用户提出新的方向时，记录与现有决定、案件逻辑、工程依赖及交付范围的关系，再调整当前工作。
- 不把候选架构、纸面推演、模拟结果或供应商文档能力记作已实现或已实测。
- 多游戏架构基础从首轮建立；多个成品游戏内容、选游戏界面、新玩法、自动生成剧本、案件编辑器、长期进度与精细评分可后置。新增同玩法游戏不能要求修改通用引擎和 UI。
