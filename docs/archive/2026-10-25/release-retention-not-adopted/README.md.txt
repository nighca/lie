## Candidate behavior

The existing main CI trigger, concurrency, coverage/typechecks, dry-run, latest-main guard and deploy gate remain. Its former combined build is split at the existing workspace boundary:

1. Build Web and snapshot **current-only** `/static/**` plus hashed `/assets/*.js|css`, sorted path/size/SHA256 inventory, repository, source SHA, run ID and attempt.
2. Read prior runs from this same repository/main/CI workflow. Verify the actual deploy step succeeded, order by its completion time, and inspect prior attempts too (a failed rerun must not erase a successful prior deployment). Restore only the latest **two** eligible deployed generations. The archive upload step must have succeeded; archive name/source SHA/run/attempt and GitHub archive digest must match. Test-only, skipped-deploy and fork/other-workflow runs do not qualify. An expired selected generation is explicitly reported/omitted, not replaced by ever-older generations.
3. Validate all bytes before merging. Same URL/same bytes deduplicates. Same URL/different bytes, missing inventory, incorrect hash/size, unexpected files, symlinks, traversal, bad provenance, failed download, missing required archive, unsupported ZIP, and exceeded bounds fail. Entry HTML, mutable manifest, fixed assets, games and API/credentials are never restored. ZIPs are parsed in memory before any filesystem extraction; no shell executes archive content. Network requests have timeouts and response byte caps; GitHub authorization is never forwarded to the signed download host. No new npm dependency.
4. Package gateway only **after** merging, then run the existing prebuilt dry-run/main gate/deploy. Upload only the frozen current-only snapshot **after the deploy step succeeds**. Upload failure after deployment fails the workflow, and a subsequent missing required archive is an explicit error rather than false continuity.

Archive identity `deployed-immutable-v1-<sourceSha>-<runAttempt>`; files include `inventory.json`. No recursive accumulation: restored files do not enter the current-only archive. Cross-run access adds only `actions: read` alongside existing `contents: read`; no PAT, account, service, R2/KV, storage writes via APIs, deletion or permission broadening. The existing artifact upload action remains the only CI archive writer.

First adoption has no prior compatible archive and reports `bootstrap:true`; it cannot recover historical hashes from coverage, Git history or Cloudflare version storage. A required archive missing from an already-adopted deployed run fails. Explicit expiration reports `bootstrap:false` with skipped run IDs. Search now completely paginates up to1000 main workflow runs with stable total_count and unique IDs, at most10 attempts/run and1000 job queries; incomplete or excessive history fails rather than inventing an empty history. The original first-page-only implementation is superseded by RC02. At most100 jobs or artifacts per run are accepted; truncated results fail. This is bounded compatibility, not an indefinite historical asset service.

Per-generation bounds: **512 files, 80MiB raw, 16MiB/file, 96MiB downloaded ZIP**; inventory256KiB; at most current+two prior generations, **1536 immutable files /240MiB raw** before URL deduplication. Bounds apply to immutable additions; existing fixed compatibility assets also remain in the deployment. Artifact TTL14days is a proposed finite archive lifetime, **not a14-day open-page guarantee**. A third prior release can disappear earlier, and browser storage can evict resources.

## Storage policy awaiting user confirmation; do not publish this candidate yet

The root's initial suggestion to enforce a256MiB cumulative archive budget was explicitly withdrawn after automatic approval review rejected treating it as authorized: a hard limit can block deployment and affects availability. **The256MiB gate is not called by the CLI or connected to CI.** Its exported `artifactStorageBudget` implementation and tests are a reviewable proposal only. Do not enable it by changing an environment flag or infer approval from passing tests.

The candidate workflow has14-day artifact retention. Current measured raw immutable bytes are **67,196,450** (94 files, about64.08MiB). Archive compression is disabled because nearly all bytes are PNG; an uncompressed ZIP has small overhead. Each deployed run adds another current-only archive even when source assets are unchanged. Restoring only two archives does **not** reduce GitHub's stored archive count. Four full archives are roughly269MB raw plus ZIP overhead;14day storage can accumulate further with frequent deployments. Private account allowance, charges and existing shared usage were not inspected. Existing coverage artifacts remain separate and also use the account allowance. Nothing was purchased or quota-adjusted.

Concrete pending option: before deploying, enumerate all repository artifacts, verify this namespace's run belongs to this repository/main/workflow, and check existing unexpired compatibility archive `size_in_bytes` plus a conservative bound for the next current-only ZIP against256MiB. Pagination/count changes, incomplete enumeration, duplicates or over1000 artifacts fail; coverage/other workflows are excluded. The proposed bound is raw current bytes +1024bytes/file +level-0 deflate block overhead +2MiB margin. At today's generation size, approximately the fourth full archive can block deployment until expiration/manual cleanup or a separately reviewed policy. This is a **repository namespace upper bound, not proof that the shared account has256MiB free**. No automatic pruning or `actions: write` is proposed here. User confirmation of the storage/release tradeoff is still required before choosing this policy or publishing the14day default. Root will present the concrete choice after code review; this document is not approval.

Other alternatives remain proposals: shorter user-approved archive lifetime, or exact bounded cleanup separately authorized and reviewed. No option was silently selected to bypass the budget rejection. No R2/KV/new account, billing increase, broad deletion, lifetime guarantee or new deployment route is introduced.
