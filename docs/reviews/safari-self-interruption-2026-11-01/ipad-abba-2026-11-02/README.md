## 数据检查

- 四组均formatVersion2/stopped/error=null/timelineTruncated=false，tracks与contexts释放成功；capture48k/AEC=true，各phase一致；B playback48k，A playback16k。
- playing均200个20ms帧，quiet-before均100帧，quiet-after100或101帧。按`sum(window.rms² × window.frames) / sum(frames)`重建各阶段aggregate、按窗口取max重建peak，全部一致，最大RMS绝对浮点误差`4.34e-19`。
- playing首帧主线程到达3/6/6/7ms，后续窗口规律推进到约3980ms；没有前一轮iPhone C那样明显缺少前静默帧。但这些时间是编码帧**收到**的时间，不是硬件采样或精确声学起播时间。
- 首10帧是约200ms样本分组，至少99.97%的本次播放期测得输入能量集中于此；其余3.8秒极低，部分窗口全零。输出结束后约1.0–1.2秒的接收窗口开始回到约`2e-4`底噪量级，不能直接命名为AEC校准、noise gate或其他具体平台机制。
- 独立复算及采集代码只读检查一致：probe/microphone/PCM encoder没有在playing期间主动置零、关麦或门控；encoder只有重采样/裁剪/量化，小信号可能量化到零。不能从零值反推浏览器具体处理。

## 结论

**本轮支持“播放边界相关的短输入峰”，不支持B是稳定修复。** 首个B的整体RMS最低，最后B反而最高，相差8.74倍/18.83dB；相邻配对B1/A1为−12.79dB，B2/A2为+3.74dB，方向反转。前次B绝对值较低不能继续当作产品改48k的依据。

这里没有ASR/STT/VAD或真实人物语音数据，也没有实际游戏自打断记录，所以仍不能确认这段输入峰就是用户所报STT的原因。纯合成音稳定段低输入不推广为真实语音AEC都正常。维持游戏16k、连续mic和自然插话；不屏蔽启播前200ms、不忽略重复STT、不关闭供应商打断。

停止扩大合成音/采样率轮次。下一步优先[用户手动真实游戏的被动事件时序](../next-live-window.md)，区分上游STT/aborted与本地stop的先后。已询问用户是否方便Mac远程Safari Web Inspector；没有自动发起会话、录音、上传音频或provider调用。若工具路线不便/无法提供所需关键事件，产品内opt-in观察需新范围确认，当前只形成提案，不实现共享接口。
