# iPhone Safari 首轮补充

2026-11-01，用户在本专项提供三份JSON，并明确：**C明显更响，出声方式也感觉不同**；没有iPhone Chrome对照。机型、系统/Safari版本未提供。不将iPad上六组条件一致的确认自动套用于iPhone。

原JSON逐字保存，bytes/SHA256及计算见[分析结果](analysis.json)。仅以文件名对应的`current`比较三组；`completed`除了前一文件current的重复，还含额外未标注轮次。原样保留，但不知道其测试条件/所属轮次，不将它们擅作同条件重复，也不与iPad合并。

| 组 | 静默前 RMS | 播放 RMS | 静默后 RMS | 静默前/播放/后帧数 |
| --- | ---: | ---: | ---: | --- |
| A，16k直接播放 | .0001505 | .0020081 | .0008449 | 96 / 200 / 100 |
| B，默认48k直接播放 | .0000437 | .0008585 | .0000177 | 100 / 200 / 100 |
| C，16k媒体流播放 | .0000252 | .0002958 | .0000289 | 72 / 200 / 101 |

三组均无error、AEC=true/capture48k、清理成功，播放有完整200帧。C前静默只收到72帧，不能当作与100帧同样完整的2秒采集基线；时间差究竟发生在采集准备、帧到达还是其他调度中，v1没有记录，不能确定。

B的绝对播放RMS比A低57.2%（−7.38dB），但静默基线也显著变化，不能据此宣布48k改善AEC。C比A低85.3%（−16.63dB），同时用户听到它明显更响/出声方式不同，存在明确输出混杂：这既不能简单解释为“输出更小所以mic更小”，也不能越过声学/路由变化直接宣布AEC更好。它支持系统音频路径确实值得核查，**不授权将C作为游戏替换方案**。

当前三个环境的B绝对输入都较低是待复现线索，非跨设备统计结论。下一轮继续聚焦用户方便的一台问题设备Safari的少量A/B，用诊断v2分时音量和帧到达时间区分启播/持续/基线；不要求iPhone补Chrome、不对C扩大试验、不开自动付费会话。根因仍未定，没有产品语音修复。
