## Recommendation: retain the narrow Worker guard

A broad `/static/*` plus `/assets/*` immutable `_headers` policy is insufficient with SPA fallback: a nonexistent resource can match the path pattern while returning index.html. The owner has tested this on the actual configured host. Official docs describe SPA handling and path-matched headers; headers are not a status/content-type-aware response filter. Version/compatibility routing behavior can differ, so use the owner's host-specific fixture results instead of asserting every Cloudflare setup returns HTML for every missing request. [SPA routing](https://developers.cloudflare.com/workers/static-assets/routing/single-page-application/), [headers](https://developers.cloudflare.com/workers/static-assets/headers/).

Exact generated `_headers` entries for only existent files are a viable limited alternative to avoid attaching immutable to unknown paths, but cannot themselves force missing resources to404/no-store. At this build they already consume94 rules (92static +2bundle), leaving6 of the documented100; two retained releases can exceed that even before new characters/resources. Grouping by43 hashes saves entries but again matches nonexistent children under a known hash. The same docs limit each header-file line to2,000 characters; no practical rule-count bottleneck exists with the guard's two prefix routes. Do not replace status-aware validation with filename appearance alone. [Header limits](https://developers.cloudflare.com/workers/static-assets/headers/).

For the existing SPA architecture, the narrow Worker guard is the smallest robust way to enforce success/non-HTML immutable and404 no-store without maintaining an asset existence table or rebuilding routing. Keep GET/HEAD/conditional304 tests, missing paths with and without validators, and platform-specific Range behavior. A304 lacking MIME needs trustworthy metadata/existence validation before long caching; the current implementation uses HEAD. Do not newly claim206 from an actual platform test that returned200. Preserve API/WS behavior and stream asset bodies rather than buffering.

**Tradeoff:** requests matching those prefixes always invoke Worker code; direct static asset service is free/unlimited, but Worker invocations follow its plan. On a free plan, exhaustion returns429 for Worker-first paths rather than bypassing the Worker. Warm browser cache hits need no request, while cold/revalidated/evicted requests still invoke the guard. This is a real availability/cost tradeoff, not just a few lines of code. No extra storage fee for Cloudflare Static Assets is documented. Current account plan/quota was not inspected. [Official billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/).

No new infrastructure permission is needed just to recommend this implementation. Root should record expected request amplification and existing plan limits before deployment, rather than suggesting the guard is cost-free or adding an unrelated approval ceremony.

## Cross-deployment hashes: current binding is not historical URL retention

An old page/old immutable manifest may request an animation or part it has not cached, after a new deployment no longer includes that hash. Browser immutable caches do not guarantee every dependent asset was fetched or that cached entries survive eviction. A miss must not return new bytes under the old hash, even when a static fallback can keep the UI usable.

I found no official Workers Static Assets guarantee that the active version's ASSETS binding exposes the union of historical paths. In fact, Cloudflare's version-affinity documentation explicitly describes a request for versionA's hashed file routed to versionB failing404 because B lacks it. Affinity concerns gradual deployment routing and is not an indefinite old-file-retention facility; it does not solve an already-open page after moving100% to a new version. Do not import Cloudflare Pages asset-retention behavior into this Workers app, or equate rollback/version storage with active URL availability. [Version affinity and static assets](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/version-affinity/).

Current fingerprinting only emits the current tree, so this remains a known compatibility limitation unless publication deliberately carries old hashes. Correct404/no-store is still better than permanently caching SPA HTML, but does not itself preserve the old page.
