# P0：供应商连接隔离调查与决策稿

2026-11-01；owner：专项 Chat `01a19557-145d-72f3-ace4-382ac03c22c9`。基线 `98d71fb9ebc2f517010598c4796c8db3014a73c7`，分支 `codex/voice-device-isolation`。**调查与待确认方案，不是已批准实现或修复交付。** [本地实验证据](README.md)独立保存；初始调查没有新增供应商会话或账户API请求、资源、secret、服务或应用改动，后续新增的获准生产连接测试另档。

## 已证实的问题与源码边界

本地现配置下同 Device、不同随机 ClientId 的第二条连接使第一条收到 close1000；第二轮没有 listen 或音频输入，足以否定“随机 ClientId 已提供并发隔离”。后续在用户明确接受顶掉其他用户的授权下，[生产双页面协议连接已一次复现顶替](production-2026-11-01.md)：A准备好后保持约3秒再建立B，A被非主动close1000，B正常准备好并保持。未比较生产与本地设备身份，不归因为历史跨用户泄露或全部旧断连；这也不是完整游戏UI真人并行问答验收。

- `apps/gateway/src/index.ts:64–66` 固定 Device/token/Agent；`relaySockets` 仅隔离本地 socket 对。600秒上限和CPU30000不能改变设备互斥。
- `apps/web/src/application/controller.ts:172–181` 的 session/character/epoch 与 `liveVoice.ts` 的 `isCurrent()` 保护当前页面状态和工具投影；未传成供应商独立身份，应保留这些保护。
- `packages/voice/src/channel.ts:200` 从 hello 取得 session_id，后续用于 listen/abort；新 session_id 不是并发可共存的证明。当前无自动重连，应保留，避免互相顶替循环。
- `apps/gateway/test/gateway.test.ts:13–29` 的 fake 每次独立echo，没有模拟同 Device 顶替；session-limit的双socket测试只验证timer独立。通过这些测试不能宣称供应商多用户隔离成立。

旧[技术发现](../../technical-discovery.md)“每轮新连接/停止旧设备资源”是历史编排措辞，当前实际上是每次启动 conversation 建新 WS、关闭本地连接，没有设备分配/删除。[旧公开语音提案](../../public-voice-launch-proposal.md)已有动态设备和协调租约备选，但均为未采用提案，不能当批准；其中3分钟等历史参数以当前600秒源码为准。原有180秒cap与CPU超限是有独立证据的旧故障，不能用本次结果覆盖。

## 新增实证与当前建议

用户提出按每个游戏过程固定Device、局内多个语音连接复用。[第二轮专用资源测试](independent-device/run-02.md)支持这条正常路径：D1在线期间动态分配D2到ready为6139ms，两者并存；同D1的A→B→A2正常关闭后换新WS，D2持续在线，未检出所设canary串入。可据此继续收敛[按局分配](per-game-device.md)的正式方案，减少每次语音重复分配，而不再将“独立Device能否并存”视为完全未知。

本轮并非生产网关实现验收。六题严格总判据5/6，第6题虽回答正确却没有新调用context工具；每轮获取最新context不能靠prompt当保证。软件Device规模许可/配额、局归属凭证、并发/晚到握手、异常断网与资源清理仍未解决，不默认批准在线管理key或新增协调服务。下述A/B/C保留为初始路线比较，不能当正式选型决定。

## 官方公开契约复核

2026-11-01仅浏览公开官方页，未查询账号API、控制台或账单。

| 对象 | 公开契约 | 对本次修复的含义 |
| --- | --- | --- |
| Device-Id | MAC设备身份，服务端验证预注册/绑定 | 不能随便换一个字符串而复用旧token便声称合法可用 |
| Client-Id | 软件生成UUID，OTA说明UUID v4 | 没有声明是同设备并发隔离开关 |
| session_id | 服务端hello返回的会话关联标识 | 不由客户端提前分配，不提供设备占用/撤销保证 |
| X-Agent-ID | 选择本连接的Agent配置 | 不证明换Agent可绕开同Device互斥 |

来源：[WebSocket协议](https://linx.qiniu.com/docs/xrobot/platform/websocket)、[OTA协议](https://linx.qiniu.com/docs/xrobot/platform/OTA)、[Agent与音色切换](https://linx.qiniu.com/docs/xrobot/platform/agent-voice-switch)。这些页面未给出同设备独立并发选项；这是本轮查阅范围，不是证明平台绝无其他能力。

[设备API](https://linx.qiniu.com/docs/xrobot/api/device)提供预注册、激活绑定、列表、解绑及删除预注册记录。批量预注册可能部分成功，需要逐项核对。这不证明允许浏览器每WS无限生成软件设备，数量、速率、token绑定/有效期和套餐限制尚待供应商或获批账户核实。

[固件接入指南§2.3](https://linx.qiniu.com/docs/xrobot/guide/xiaozhi-firmware)明确解绑不会立即终止当前通话。因此解绑/删除不能当作旧上游已停止或设备可安全复用的ack。[计费规则](https://linx.qiniu.com/docs/xrobot/billing/resource-usage-billing)按设备会话连接至结束的时长计算UID用量；静默连接也可能耗用额度，本批未查实际账单。

## 路线比较与建议

| 候选 | 优点 | 必须解决的依赖/代价 |
| --- | --- | --- |
| A：供应商原生独立Web会话能力 | 若存在，可保留薄网关和现有浏览器接口 | 公开资料未证实；需明确端点/字段、隔离范围及可验收契约 |
| B：每次WS独立新Device，不复用活跃身份 | 不需要共享空闲设备的争抢锁 | 软件设备许可、配额、绑定/OTA延迟；管理key在线化、响应丢失、清理失败、资源持续增长；不能无界创建 |
| C：有限设备池＋权威协调者 | 容量和资源数明确 | 新增跨Worker持久协调责任；所有上游握手/关闭必须归协调者所有；不确定设备隔离会降低可用容量；耗尽体验需确认 |

**建议先确认A，以及B/C共同依赖的软件设备许可与会话终止契约，再定路线。** 如果没有A，不采用仅改ClientId/Agent、Worker内存Map池或自动重连。C若采用Durable Object等托管协调器，是需要用户确认的新架构/资源；本文不选择产品、不创建资源。B不是“无状态小改”，供应商资源清单和恢复清理同样承担持久状态责任。

### C必须满足的安全条件（工程建议，未批准）

1. 单一权威协调者先持久化独占，再拨号；租约有owner和递增代次。多Worker不能同时分到同Device。浏览器不携带可重放的device lease或token。
2. 协调者拥有实际上游生命周期；旧owner的release、timer、晚到WS和清理响应只能作用于原代次。仅有数据库TTL锁仍不足：供应商不识别fencing代次，旧请求晚到仍可能顶替新会话。
3. 状态至少区分空闲、建立中、活跃、关闭中、终止不确定。只有可靠确认旧上游结束、且顺序复用无状态泄漏后才能恢复空闲；调用close、TTL到期、解绑或实例失联都不等于确认。
4. 不确定资源进入隔离，不自动借给下一人；没有可信终止上限/核对办法时不得仅等固定几秒回收。容量耗尽拒绝新请求、保护已有会话，不偷偷共享或扩容。可能耗尽全部容量是需要明确接受和解决的可用性边界。

### 需要用户/供应商决定的最小事项

- 供应商是否有受支持的Web/SaaS独立会话入口？重复连接的唯一性键究竟是什么？
- 是否允许软件设备，设备/活跃连接上限、API速率、额外费用及token绑定/期限是什么？是否能可靠查询/终止某条会话？
- 无记忆配置下设备顺序复用是否保证短期上下文、MCP工具状态和未完成生成被清除？
- 若必须采用C，是否接受新增协调服务、明确容量与“繁忙稍后重试”？若B，是否接受管理凭据在线化、有限创建与持续清理责任？未经确认不实现。

可直接转发的[供应商询问稿](vendor-inquiry.md)已准备，包含最小账户只读核实清单。尚未向供应商发送；渠道待用户指定，外发需明确对象和内容授权。没有要求用户在Chat贴token或提供账户秘密。

## 可执行验收与授权边界

方案确定后，源代码范围拟为gateway身份分配与生命周期、相应test/config及必要Web错误状态；先向总协调申领具体文件ownership。保留 `/api/voice`、浏览器游戏状态、角色MCP、Origin/查询限制、600秒cap及64KiB边界；容量专属提示需新契约，原生浏览器WS握手失败通常无法读取HTTP错误详情，status ready也不是容量预留。

离线最少验证：同Device踢线fake重现；两连接不同有效身份交错text/binary、关A不关B；两个gateway实例同时争一设备仅一成功；耗尽不拨上游；取消后迟到分配/WS/旧release不可影响新owner；初始化失败与清理幂等；关闭不确定资源保持隔离；无凭据泄漏。fake只证明本地所有权逻辑。

真实验证必须另获设备owner与时间窗授权。建议先提交**最多两个专用Device、一次双连接、每条ready后保持3秒、总截止30秒、无listen/麦克风、记录CLOSEDack**的具体申请；必须先明确这些Device如何合法取得、和现有用户资源不重叠。UID用量可能产生，不能承诺零费用。此申请目前未批准，不执行。若连接并存通过，仍需另行批准有界合成人物问答，验证上下文/工具/音频及顺序复用；静默并存不能代替数据隔离。

最终发布验收必须区分：本地逻辑自动化、真实专用设备隔离、受控浏览器体验、正式配置/发布验证。任何一层缺失就明确报告，不用fake或历史独立设备测试替代本次真实结果。
