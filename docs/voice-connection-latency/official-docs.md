# 灵矽官方文档与连接优化候选

2026-10-25；用户在本专项明确要求结合灵矽官方产品文档寻找思路。本文是首轮[实测报告](README.md)的后续，只读公开文档，未新增真实调用、provider配置、服务或实现。所有候选仍未批准。根协调已通知用户授权停用本地8787/8788，由另一owner执行；本专项不恢复环境，也不因旧服务记录自动追加测试。

## 文档带来的候选思路

### 1. 保持当前隔离，先查固定上游与动态路由

[WebSocket协议](https://linx.qiniu.com/docs/xrobot/platform/websocket)提供固定WSS地址，并建议优先使用OTA动态返回的地址；[OTA协议](https://linx.qiniu.com/docs/xrobot/platform/OTA)描述已绑定设备返回websocket.url及token。当前gateway使用固定官方地址，因此多出一个值得核对的候选：设备实际推荐的地址是否不同、是否有路由差异。

**推断，不是文档承诺：** 如果动态地址有不同接入路径，可能影响实测最大的upgrade包络；如果返回同一地址，则本候选没有路由收益。文档没有延迟SLA、区域就近保证或“动态地址一定更快”的说明。未发OTA请求、未查真实device/token、未替换地址。

若后续批准验证，应先在网关私密环境做最少一次配置核对，再按同环境、有界次数做对照；不要给每次切人再串入一次OTA。token必须留在网关，动态URL仍需固定可信目标校验，不能变任意代理或任意地址携带认证。认证刷新/缓存生命周期是需明确的新设计，不能把“改一行URL”视为完整方案。

优先级：先用生产TLS与Worker同请求阶段时间区分本地代理/宿主和上游，若upgrade仍主导，再考虑路由对照。现有3次样本无法决定哪个环境慢。

### 2. hello直接注入当前人物资料，减少后续工具调用

协议的`agent_params.custom_replace_prompt`允许在建立连接时替换系统提示词占位符。这为“一条连接固定一个人物”提供了另一种上下文传递方式，理论上可能减少回答前读取MCP context的往返。

**本任务收益有限且未证明：** 这不会免除WS upgrade或hello；本组hello后工具列表完成仅需0.5–1ms，没有证据可将前面约0.42秒hello包络全部归给工具发现。提示词占位符也不是任意完整systemPrompt覆盖API；要准备模板、处理history更新和帧容量，还改变现已验证的工具契约及内容传输边界。因此不把它当连接等待的首选小修，也不默认改共享agent配置。可另归回答延迟研究。

### 3. 单个备用连接预热，避免每个角色都常连

从实测推断：若在用户仍与A对话时准备一个没有收音的备用连接，选B时再绑定B的上下文和音色，理论上能遮蔽部分upgrade/hello等待。它比给所有角色各保留一个连接需要更少的同时连接，但仍改变生命周期和潜在费用。

**未获官方保证、未验证：** 所读协议/设备API未给同一Device-Id多连接的并发上限、互斥/顶号行为、空闲计费、备用连接未listen的超时保证，也未保证工具调用发生前可安全延后人物绑定。现channel将tools/voiceId固定在创建参数中，controller/epoch资源所有权也需要重审。当前工具在ready前就可能出现调用，不能让备用连接读取A或其他角色资料。3分钟网关限制从relay创建开始，预热会消耗它。

这是需要用户决定的候选，不是当前推荐直接实现。若选择它，应先确认供应商同device并发契约，再确定何时建备用、最多几条、停止/取消是否全关、多久失效、额度如何记录、切换连点与旧事件如何处理；验收必须包含跨人物/跨局记忆和迟到音频隔离。无新许可不做付费并发探测。

### 4. 每人物保留一条连接，或同一连接reset后复用

每人物一条连接理论上让回切复用准备，但3/4/更多人物会增加并发资源、空闲寿命与管理复杂度，官方所读文档尚无可依据的配额保证。单连接reset后复用则缺少明确协议和确认屏障。目前两者都不能作为已获支持的方案。

[第三方接入指南](https://linx.qiniu.com/docs/xrobot/guide/third-app)里的reset是自定义业务消息透传示例，不是灵矽内置清空LLM上下文命令。把LLM与历史管理迁到自有业务服务属于较大架构变化，且本身不会让WS建立更快，本轮不扩展。

## 其他已查资料与排除项

- [端侧MCP](https://linx.qiniu.com/docs/xrobot/mcp/hardware-mcp)描述initialize/list/call发现流程；没有声明设备可跳过发现便开始依赖角色工具的对话。
- [设备工具描述API](https://linx.qiniu.com/docs/xrobot/api/device-tool)是用户工具描述/前置提示词管理，不是端侧工具已注册、也不是免握手的证明；未调用该API。
- [智能体API](https://linx.qiniu.com/docs/xrobot/api/agent)的空闲断连配置不是快速握手参数，不能靠延长它证明“保活就安全”；当前网关另有180秒上限。模型/ASR/VAD/TTS配置暂不改动。
- [客户端demo](https://linx.qiniu.com/docs/xrobot/guide/client-demo)是C++ Linux/macOS方案，参考了连接/监听/TTS状态说明；没有从中找到浏览器角色切换的已验证reset机制。仅打开了官方链接的开源仓库首页，未安装或运行示例。
- [FAQ](https://linx.qiniu.com/docs/xrobot/faq/faq/)主要讨论硬件接入与配置更新，不提供连接建立耗时保证。未采用其中固件重置/重启建议来干预本项目。
- `play_buffer_duration`涉及音频发送/播放缓冲，不能把默认1000ms当成本次尚未收到音频前的连接等待；PCM换Opus、VAD参数等也没有消除此处upgrade包络的证据。

## 当前推荐与后续可执行边界

首先拆清连接包络，保留新人物独立连接；路由核对是本轮官方资料带来的较小候选。若目标是把切人做到接近即时，则单备用连接值得作为下一份具体方案讨论，但先解决同设备并发/费用/角色绑定契约。没有把用户的“参考官方文档”扩大为预连接、多连接或配置修改许可。

本轮公开资料未给出可直接证明显著加速、且保持现生命周期的小参数。此结论是这批资料和3次本地样本的边界，不是供应商能力的穷尽结论。后续需供应商澄清的问题：同一device可并发几条WS、是否有明确会话reset与完成ack、reset是否清短期上下文及工具缓存、旧音频跨reset如何标记/清理、未listen连接寿命/计费、是否有更合适的接入路由。
