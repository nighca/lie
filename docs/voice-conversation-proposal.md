优先读取了新提供的 `qiniu_ai_api_docs` OpenAPI 工具。其当前目录是“AI模型接口”（通用模型/视频等接口），未覆盖灵矽 xrobot 的上述会话协议，故改查灵矽官方网站；没有调用其中任何视频接口。官方 WebSocket 的部分通用音频说明偏向半双工，不能据此推断 realtime 期间应丢弃所有播放帧，需以专项实测裁定。

## 推荐生命周期

**同一人物、一次显式开启期间复用一条 realtime WebSocket；结束或人物边界就关闭。** 保留浏览器会话、按人物历史和 MCP 知识过滤，Worker仍只负责传输，不新增 DB、设备池或长期记忆。

1. 开启按钮：显示“准备语音”，在这次用户手势下准备播放上下文、申请麦克风并连接服务；只在用户确认此提案后实现。准备期间不上传 PCM、不缓存待发送人声，界面提示准备完成后再说话。失败/取消必须回收已成功的其他资源。
2. hello 音频协商、MCP 工具注册响应发出、采集管线就绪后，发送一次 realtime listen.start，开始持续上传 PCM。不能靠固定延时假定工具已注册。
3. 静听、用户说话、等待回答、播放回答是同一会话内的状态；普通 TTS stop 只完成一轮，播放尾音结束后回到聆听，不关闭 socket/mic，不需再次点击。等待时继续收音以支持接着说话/打断。
4. 服务端明确 aborted stop 时立即清空本地待播节点，结算已显示的部分转写为 interrupted，保持采集。下一次合法 TTS start 可恢复播放。首版以供应商人声检测为依据，不新增仅按音量触发的端侧 VAD，避免将外放回声误当玩家。
5. 再次点击、切换人物、打开指认、结案、重开、离开/隐藏页面：统一结束，停止 tracks/worklet/player、关闭 AudioContext/socket、撤销 MCP 调用、增加 epoch。旧事件/旧工具不能写回新人物或新局。切人后默认需再次点击开启；不在旧连接里只换 profile 后继续。
6. 异常断线、后台恢复或达到现有网关 3 分钟连接上限：立即停采集与播放，保留转写，明确提示重开语音。首版不自动恢复麦克风、不重发旧 PCM、不重放未确认的上一问；玩家主动再次开启时新建连接，仅提供当前人物历史。

这意味着“持续收音”仅发生在用户显式开启、当前页面可见、当前人物未改变的一段受限会话内。不会悄悄将当前按轮录音改成页面常驻麦克风，也不擅自延长网关限制；3 分钟连接限制与未来游戏审问时限是两件事。

## 与当前实现的冲突及最小模块变更

| 模块 | 需要调整的职责/接口 |
| --- | --- |
| 应用 controller | 保留 epoch 与按人物历史；会话开关独立于 listening/thinking/speaking；普通回答结束不再调用 stopVoice；startInput/finishInput 迁为显式 startConversation/endConversation（名称待实施协调） |
| liveVoice | 一个会话持有 player、channel、microphone；区分 answer-ended 与 conversation-ended；任意部分初始化失败均可幂等关闭；禁止旧 scope 回包 |
| voice/channel | 显式 realtime 模式；ready 不仅依赖 hello，另跟踪工具列表回复已发出；暴露 `tts.stop` aborted 标记；修复打断后新轮恢复门控，兼容重复/迟到 stop；音色作为一次会话的可选供应商参数 |
| microphone/player | 保留16kHz PCM编码、echoCancellation/noiseSuppression；player增加清空当前播放但不结束整个会话的明确能力；后台/权限撤销/关闭释放全部资源 |
| UI | 按钮始终允许结束准备或持续会话；显示“正在聆听/正在回答”等状态，明确麦克风仍开着；切人/指认后不继续偷听。暂不制作具体样式 |
| Worker | 维持固定上游、鉴权、帧限制和3分钟期限；无需新游戏状态。公开访客身份/设备分配仍是独立未解决事项 |

现有方案每轮新WS能切断供应商的瞬时上下文；改为同人物长连接会保留该连接的自然上下文。这不扩大角色可见知识：每轮 MCP 仍读取当前人物的 browser history/profile，不共享其他人物；但被打断且模型已生成、用户未听见的内容可能留在供应商短期上下文。提示词只能约束，不能声称删除成功，需用专门测试确认不会拿未听见的信息当已告知。不能为省握手把不同人物塞入一条长连接。

现有协议没有可靠的逐回答音频 ID；同一连接内仅按 session_id 无法区分旧回答迟到音频。必须实测 aborted stop→新 start 的排序和音频边界；若无稳定边界，应向供应商澄清或另提降级方案，不用固定延时掩盖串音。

## 连接等待与回声

当前串行等待包含：播放 AudioContext resume → Worker/上游WS握手 → hello → getUserMedia授权/设备启动 → AudioWorklet加载和采集AudioContext resume。并不包含模型回答耗时；当前每轮重新发生。

先记录仅耗时与事件类型的本地阶段指标：点击→权限完成、WS open、hello、tools-list回复、worklet ready、首个上传帧；另记用户停顿→STT、工具调用、TTS start、首帧实际播放。权限等待单列，不以几次样本宣称p95。

在上述生命周期确定后，允许同次点击内并行准备连接与采集，未ready前丢弃采集帧，避免积压；同人物后续轮次自然省去重新建连，不另做manual模式的跨轮持有。先测耳机基线，再测外放：浏览器AEC并非消除回声的保证，须覆盖外放自打断、扬声器音量和真人插话。单纯在AI回答时关麦会破坏用户的打断目标，不作为默认修复。

## 验证与实施门槛

- 自动化：fake provider连续三轮、不在普通stop关闭；aborted立即清播放且下一轮能播；重复/迟到事件、MCP取消、切人/指认/重开/隐藏/权限拒绝/连接超时；并行初始化任一失败回收其余资源；断线不自动重采集、不重发音频；原按人物知识和历史隔离测试保留。
- 集成：真实workerd文本/binary/close、鉴权/帧限制/期限不回归。供应商fake通过不能作为真实VAD证明。
- 真机受控实验（待方案确认后安排）：专用设备、合成无秘密角色，先同人物三轮停顿自动答，再真人插话、连续两次打断/恢复、A→B→A、重开、两设备并行、断网和上限；耳机及外放各测，记录阶段耗时、上下文工具调用数、尾音/误触发和泄露情况。不得占用用户正在试玩的设备；不存原始人声或私密上下文到日志。
- 能力实验通过后才展开应用改造。若realtime无法可靠停止/恢复本地音频或隔离边界不稳定，带证据重新讨论，不擅自交付半双工替代目标。

## 用户确认记录与剩余边界

1. 是否同意以上 realtime、同人物长连接且每轮继续读取角色上下文的方案，先进行受控能力实验？长连接允许当前人物的供应商会话内短期上下文。
